1. Резюме для руководства

Как это работает — два жизненных цикла (см. рис. 1)

1А. Пользователь (сотрудник)

На одной схеме: ① вход (система входа → веб-шлюз) → ② отправка (сотрудник → браузер → шлюз → сервер → база) → параллельно ③ уведомление получателю и ④ файлы (сервер → хранилище → архив по срокам).

1Б. Администратор

Единая схема с ветвлением от админ-панели — четыре типовых сценария:

  • Политики и организации — сроки хранения, привязка пользователей к org.
  • Legal hold — заморозка автоматического удаления по запросу юристов.
  • Ошибочное удаление — сообщение скрыто в UI (soft-delete), но данные остаются в базе/архиве; админ заказывает export (ZIP) для восстановления по процедуре заказчика (не «кнопка отмены» в чате).
  • Расследование — журнал аудита (кто менял политики, запускал export) и мониторинг фоновой очистки (purge).

Сбой админ-цикла не блокирует переписку сотрудников. Для аварийного отката на уровне всей системы — backup/restore по runbook (§15, профиль Pilot/Standard/Enterprise).

Korus Messenger (AvandocMsg) — корпоративный мессенджер для организаций: переписка, файлы, видеозвонки, управление сроками хранения данных и инструменты для юридического и внутреннего контроля. Работает в браузере, может устанавливаться как приложение (PWA). Предназначен для изолированных контуров — на серверах заказчика или в частном облаке.

Что уже работает

  • Вход, регистрация, безопасный выход и автоматическое продление сессии
  • Личные и групповые чаты: отправка, редактирование, удаление, пересылка, реакции, закрепление, ответы, сообщения с автоудалением
  • Мгновенная доставка в браузере; восстановление после обрыва связи
  • Контакты, поиск коллег и поиск по тексту переписки
  • Файлы: загрузка, просмотр, скачивание, публичные ссылки с отзывом
  • Личное «Хранилище» для сохранённых сообщений
  • Экспорт переписки в архив (JSON/ZIP)
  • Видеозвонки и демонстрация экрана из чата
  • Админ-панель: организации, политики хранения, legal hold, журнал аудита
  • Интерфейс на 6 языках (русский, английский и др.)
  • Сквозное шифрование — технически готово; массовое включение в промышленной среде после согласования с безопасностью

Что нужно до промышленного запуска

  • Защищённое соединение (HTTPS) для всех пользователей
  • Формальное одобрение усиленного шифрования (Product / Security / Ops)
  • Production-уведомления в браузере (Web Push)
  • Сервер для стабильных звонков за корпоративным firewall (TURN)
  • Согласованная с юристами политика полноты выгрузок для комплаенса

5. Кейсы использования

Формат: ситуация → действия → результат. Всего 27 сценариев.

5.1 Сотрудник

КУ-01: Переписка с коллегой Реализовано

Ситуация: Нужно обсудить задачу с коллегой из другого отдела.
Действия: Найти коллегу → открыть чат → написать.
Результат: Сообщение доставлено мгновенно.

КУ-02: Проектная группа Реализовано

Ситуация: Запуск проекта на 8 человек.
Действия: Создать группу → пригласить участников.
Результат: Общая лента и обмен файлами.

КУ-03: Файл внешнему партнёру Реализовано

Ситуация: Передать PDF контрагенту без аккаунта.
Действия: Прикрепить файл → публичная ссылка → отправить.
Результат: Партнёр скачивает; ссылку можно отозвать.

КУ-04: «Хранилище» Реализовано

Ситуация: Сохранить регламент из группового чата.
Действия: Переслать сообщение в «Хранилище».
Результат: Копия сохраняется лично.

КУ-05: Сообщение с автоудалением Реализовано

Ситуация: Передать одноразовый код.
Действия: Отправить с таймером (TTL).
Результат: После времени сообщение исчезает.

КУ-06: Read receipts Реализовано

Ситуация: Проверить, кто прочитал объявление.
Действия: Открыть сообщение → список прочитавших.
Результат: Видно, кто ознакомился.

КУ-07: Обрыв Wi‑Fi Реализовано

Ситуация: Связь пропала в метро и восстановилась.
Действия: Открыть мессенджер.
Результат: Сессия и сообщения восстанавливаются.

КУ-08: Видеозвонок Частично

Ситуация: Обсудить голосом и показать экран.
Действия: «Звонок» в группе → камера/экран.
Результат: Конференция; за firewall может нужен TURN.

КУ-09: Смена языка Реализовано

Ситуация: Предпочитаемый язык интерфейса.
Действия: Настройки → язык.
Результат: Интерфейс переключается.

КУ-10: Блокировка пользователя Реализовано

Ситуация: Нежелательные сообщения.
Действия: Настройки → заблокировать.
Результат: Заблокированный не может писать.

7. Безопасность и соответствие

Разделение данных

Пользователи организованы по организациям. Политики хранения и legal hold задаются на уровне организации и при необходимости — отдельного чата.

Журнал аудита

Все значимые административные действия (смена политик, экспорт, legal hold) фиксируются: кто, когда, что сделал.

Защита от злоупотреблений

  • Ограничение частоты попыток входа (защита от перебора паролей)
  • Доступ к чатам только участникам
  • Блокировки учитываются при поиске и доставке

Сквозное шифрование (E2EE)

РежимЧто видит сервер
Без E2EEТекст сообщений (хранится на сервере организации)
С E2EEТолько «конверт» — расшифровка на устройстве пользователя

Частично — работает в тестовой среде; промышленное включение после согласования с безопасностью.

10. Ресурсы серверов и нагрузка

Следующий рисунок — насколько оптимизация §12 снижает потребление RAM относительно базовой конфигурации §10.2.

Важно
Все цифры — ориентиры для планирования. Перед промышленным запуском рекомендуется нагрузочное тестирование на 10–20% целевой нагрузки. Активные видеозвонки и прямые эфиры могут удвоить требования к сети и процессору.

10.1 Как считается нагрузка (простыми словами)

Для оценки берём число зарегистрированных пользователей и типичные коэффициенты активности корпоративного мессенджера:

DAU (активных в день) = Пользователи × доля активных
Пик онлайн = DAU × доля одновременно в сети
Сообщений в день = DAU × сообщений на человека
Пик сообщений/сек ≈ (сообщений в день ÷ 86400) × 3,5

11. Критерии приёмки продукта

  1. Пользователь выполняет все основные сценарии из §5 через веб-браузер.
  2. Автотесты UI: 27+ сценариев проходят на тестовом стенде.
  3. Администратор управляет организациями, политиками хранения и аудитом через веб-консоль.
  4. Production: HTTPS, секреты не в открытом виде, sign-off E2EE перед массовым включением.
  5. Экспорт и ретенция: окончательное удаление только после прохождения export gate.
  6. Локализация: интерфейс минимум на русском и английском.
  7. Инфраструктура (§12): FR-OPT-01…07 реализованы; целевые §10.4 подтверждаются load test на stage при go-live.
  8. Комплаенс (§14): export с индикатором полноты; legal hold блокирует purge; audit admin-действий.
  9. SLA (§15): согласованные RPO/RTO по профилю; сообщения не теряются при деградации P1.
  10. Профиль (§16): ограничения Pilot доведены до заказчика до запуска.
  11. Интеграции (§13): согласованы сценарии SSO и Bot API; реализованные каналы описаны для IT.

12. Оптимизация инфраструктуры

Реализовано — spec 006: волны 1–3 закрыты (FR-OPT-01…07 в коде, smokes на QEMU, outer gate 30/30). В roadmap: FR-OPT-08 (dedup файлов), FR-OPT-09 (sharding), formal load test §12.3 на stage (k6-скрипты готовы). Dev/QEMU по умолчанию — korus_deploy_profile: standard (full-server); pilot — явный override (см. deploy/ansible/inventory/qemu/group_vars/all.yml, deploy/qemu/RESOURCES.md).

12.1 Зачем это нужно

  1. Пилот на modest hardware — десятки ГБ RAM, а не сотни.
  2. Больше сотрудников на том же сервере по мере роста.
  3. Длинная история без линейного роста дисков (сжатие архива, dedup файлов).

18.5 Пример D — рост диска (бухгалтерия, 100k users)
