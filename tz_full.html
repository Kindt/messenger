1. Метаданные, цели, границы

Проект: Авандок.Мессенджер
Функционально: чаты/контакты/статусы/presence/файлы/группы/поиск/боты + потоковое видео + аудио/видео звонки + “Хранилище”.
Серверный стек: Java 17, Tomcat; без Spring
Допускаются библиотеки (JDBC/Hikari/Flyway/NATS client/Jersey/Lettuce и т.п.), но не использовать Spring Boot/MVC/Security.
Комментарий для однозначности: “без Spring” означает отсутствие Spring как фреймворка и его модулей. Использование независимых библиотек разрешено.
Хранилища: PostgreSQL (Hot + Archive), Redis, MinIO (S3), Deep Archive (S3 chunks)
История сообщений хранится в БД и/или Deep Archive; архив бессрочный при отсутствии политик очистки.
Очереди: NATS + JetStream (at-least-once)
Повторы возможны; обработчики обязаны быть идемпотентными.
Поиск: SolrCloud + ZooKeeper
SolrCloud индексирует hot+archive+deep; ZooKeeper используется как компонент SolrCloud.
Нагрузка (стартовые ожидания): ≥ 1 000 000 пользователей; ≥ 20 000 групп; ≥ 100 000 000 сообщений/день
Эти цифры определяют необходимость Hot/Archive/Deep tiers, SolrCloud и асинхронных воркеров.
Границы 1 этапа (однозначность):
1 этап включает каркас серверов/воркеров/инфраструктуры, минимальные клиенты, Bot API, поиск, файлы, уведомления, live/calls, а также dev/prod стенды. Детальные спецификации всех endpoint’ов — отдельные документы (см. «Вне рамок»).

2. Термины и правила трактовки

  • Soft-delete — логическое удаление; физически данные остаются на сервере.
  • TTL — истечение видимости (скрытие), без физического удаления.
  • Online — активность пользователя ≤ 60 секунд.
  • Hidden mode — пользователь/группа не попадают в поиск/импорт согласно настройкам.
  • Полная блокировка — заблокированный не видит сообщения/аватар/статус и не может упоминать.
  • Bot API — внешние боты, webhook и long-poll, at-least-once, event_id.
  • Hot DB — оперативная БД для последних данных.
  • Archive DB — архивная БД для полной истории (до Deep Archive политики).
  • Deep Archive — файловый сжатый архив (чанки в S3/MinIO), куда перемещаются тела сообщений по политике.
  • Версия сообщения — версия контента (текст/вложения/превью/soft-delete/edit как контент), не включает receipts/presence.
  • Доставка сообщений — at-least-once; дедуп по (sender_id, chat_id, client_msg_id).
  • E2EE — end-to-end encryption. В проекте: обязательно для calls и для live ≤200 (WebRTC), но не для HLS режима.
Правило однозначности для “поиск всегда находит”:
Solr индексирует текст сразу после записи в Hot и хранит индекс независимо от tier. При выдаче результата сервер догружает тело из Hot/Archive/Deep (fallback обязателен).

7. Регистрация (OTP), аутентификация, устройства

  • Регистрация: телефон (E.164) + пароль + OTP из SMS.
  • OTP: 6 цифр, TTL 5 минут, 10 попыток.
  • Rate-limit OTP: по телефону.
  • Сброс пароля: через OTP (обязательно).
  • Мультидевайс: не ограничено.
  • Refresh token: один на устройство; хранить безопасно (желательно хэш).
  • Logout: с устройства и со всех устройств (оба варианта обязательны).
Однозначность: “один refresh token на устройство” означает, что device_id обязателен в модели данных и в выдаче токенов.

8. Приватность, скрытый режим, online/last seen

  • Hidden mode: параметризуемый, настраивается при установке и в аккаунте.
  • Online: активность ≤ 60 секунд; presence в Redis.
  • Last seen: показывать только контактам.
  • Логи: текст сообщений не логировать (включая прокси/воркеры).

9. Контакты, импорт, поиск

  • Контакты: личный список на пользователя.
  • Импорт: по хэшам телефонов (компромисс); телефон хранится E.164.
  • Ручной поиск: доступен всем (телефон/имя/id групп), но выдача только не скрытых; лимиты задаёт системный админ.
  • Поиск сообщений в группах: доступен всем участникам группы; hidden mode не скрывает сообщения внутри группы от участников.

10. Блокировки

  • Тип блокировки: полная.
  • Эффект: заблокированный не видит сообщения/аватар/статус, не может упоминать.
  • Группы: блокируемый не видит сообщения блокирующего в группе; скрывать quoted/preview чтобы не было утечек.
  • Поиск: заблокированный не должен находить сообщения блокирующего через поиск (ACL post-filter на сервере).
  • Добавление в группу: B не может добавить A, если A заблокировал B.
Однозначность для quoted/preview:
Если сообщение содержит цитату/превью сообщения заблокированного пользователя, сервер должен скрывать соответствующие поля, чтобы не утекал текст/метаданные.

11. Чаты (1:1/группы), роли, инвайты

  • P2P создание: автоматически при первом сообщении (endpoint создания не обязателен).
  • Группы: до 10k участников на 1 этапе (архитектура должна позволять рост).
  • Роли: owner/admin/member.
  • Инвайты: по ссылке; параметры инвайта — часть настроек группы.
  • Mute: замьюченные чаты не отправляют push (единое правило для mobile/web/desktop).

12. Сообщения: история, статусы, редактирование, удаление, TTL, версии

12.1 История и синхронизация

  • История: PostgreSQL; синхронизация по времени; сервер — источник истины.
  • Hot/Archive/Deep: см. раздел 13.

12.2 Статусы delivered/read (агрегированные)

  • Статусы: delivered/read по пользователю в чате, агрегированно.
  • Однозначность: не хранить receipts на каждое сообщение каждому участнику; хранить “upto msg_id” или эквивалент.

12.3 Функции сообщений (обязательные)

  • редактирование, удаление, реакции, ответы, пересылка, непрочитанные, закрепление — обязательны.

12.4 Удаление/TTL

  • Удалить у всех: автор/админ, без ограничения по времени; физического удаления нет (soft-delete).
  • Показать удалённые: только админам (системным и группы).
  • TTL: на чат и на сообщение; скрытие без физического удаления.

12.5 Доставка и дедуп

  • Гарантия: at-least-once.
  • Дедуп: (sender_id, chat_id, client_msg_id) — уникальный индекс/идемпотентная вставка.

12.6 Версионирование контента сообщения

  • Хранить все версии: да.
  • UI: показывать последнюю актуальную версию.
  • Поиск: искать по последней актуальной версии (Solr обновляется при редактировании).
  • Права редактирования: личка — только свои; группы — свои + admin может редактировать чужие.
  • Доступ к истории версий: только админам (системным и группы).
Комментарий для однозначности (версии):
“Версия сообщения” относится к контенту (текст/вложения/превью/soft-delete/edit как контент). Receipts/presence не входят в версию.

13. Hot/Archive/Deep: оперативная, архивная и глубокая архивная системы

13.1 Hot DB

  • Hot политика: хранить 7 дней.
  • Hot лимит: 10 000 сообщений на чат; при превышении переносить старые в Archive даже если моложе 7 дней.

13.2 Archive DB

  • Archive бессрочно: да (если политики не включены).
  • Задержка Hot→Archive: допустима; поиск должен находить независимо от задержки (через Solr).

13.3 Deep Archive

  • Политики: предусмотреть включение политик очистки/перекладывания.
  • Модель перемещения: A — тело сообщения удаляется из Archive DB и хранится в Deep Archive; в Archive остаются метаданные и указатель.
  • Формат: чанки по времени (день/неделя/месяц) + компрессия; интервал — конфиг.
  • Целостность: hash чанка обязателен.
  • Доступность: допустимы доп. задержки при подгрузке Deep Archive; UI может показывать “загрузка архива”.
Однозначность “поиск всегда находит”:
Solr индексирует текст сразу после записи в Hot и хранит индекс независимо от tier. При выдаче результата сервер догружает тело из Hot/Archive/Deep (fallback обязателен). Если тело в Deep — сервер читает chunk по pointer + проверяет hash.

14. Поиск: SolrCloud + ZooKeeper

  • SolrCloud: обязателен; индексировать сообщения (актуальная версия), пользователей, группы, (опц.) аудит.
  • ZooKeeper: компонент SolrCloud.
  • ACL: post-filter на сервере (membership/blocks/hidden/удалённые/права “показать удалённые”).
  • Шарды: стартовать с минимального набора; масштабировать по росту индекса/нагрузке.
Комментарий для однозначности (ACL):
Solr возвращает кандидатов. Сервер обязан проверять права на каждый результат перед возвратом клиенту.
Это относится и к blocked, и к hidden, и к “показать удалённые”.

15. Файлы/медиа: MinIO, proxy, публичные ссылки, ресайз

  • Хранилище: MinIO (S3) обязательно.
  • Лимит файла: 10 МБ (1 этап).
  • Доступ: через собственный proxy (проверка прав + on-the-fly ресайз).
  • Публичные ссылки: поддержать A/B/C.
  • TTL ссылок: дефолт 7 дней; настраивается в конфиге.
  • Revoke: не требуется на 1 этапе.
  • Ресайз для public: разрешён без авторизации; обязательны rate-limit/DoS защита.
Однозначность A/B/C:
A — доступ всем по ссылке; B — только авторизованным; C — одноразовая/пароль/срок. По умолчанию TTL=7 дней (конфиг). На 1 этапе отзыв ссылок не обязателен.

16. Превью ссылок, миниатюры

  • Превью ссылок: делает сервер (OpenGraph).
  • SSRF политики: детально позже; на 1 этапе разрешить все домены.
  • Миниатюры: PNG + кадр видео; ресайз on-the-fly через proxy.
Комментарий для однозначности (превью):
На 1 этапе разрешить все домены означает: сервер делает fetch без allowlist. Это временно и должно быть отмечено как риск.

17. Bot API

  • Боты: внешние приложения; self-host возможен; боты не выполняются на основном сервере.
  • Владение: user_id + optional org_id.
  • Упоминания: @botname глобально уникален.
  • Права: MENTIONS_ONLY (по умолчанию) и READ_ALL (включается админом группы).
  • События: message/mention, join/left, callback, message_deleted/edited.
  • Методы: sendMessage, deleteMessage, ban/mute, setTitle, pinMessage — обязательны на 1 этапе.
  • Доставка: webhook и long-poll; at-least-once + event_id; гарантированный webhook = JetStream + ретраи.
  • Экспорт: protobuf + compression, одноразовая ссылка; replay локальный и серверный; аудит экспорта обязателен.
Однозначность (дедуп для ботов):
Бот обязан дедуплицировать события по event_id. Сервер доставляет at-least-once, повторы допустимы.

18. Уведомления: mobile push + аналоги Web/Desktop

18.1 Mobile push (Android/iOS)

  • Payload: sender, chat/group, text (если разрешено), media_type.
  • Текст уведомления: формирует клиент; сервер отправляет структурированные поля.
  • Настройки пользователя: отключение показа текста в push.
  • Mute/Blocks: если отправитель заблокирован или чат замьючен — push не отправлять.

18.2 Web уведомления

  • Основной канал: Web Push (Service Worker + Push API + VAPID).
  • Fallback: WebSocket события при открытой вкладке.
  • Опционально: email как резерв.

18.3 Desktop уведомления

  • Основной канал: WS + локальные нотификации ОС, если приложение запущено, но не в фокусе.
  • Если приложение выключено: полноценный push требует отдельного агента/службы (вне базового объёма); возможен email.

18.4 Уведомления о звонках

  • Mute calls: отдельная настройка от mute чата.
  • Каналы: mobile high priority push + WS (web/desktop) при активном клиенте.

19. Realtime: WebSocket, presence, typing

  • WS: realtime обмен сообщениями и событиями; auto-reconnect обязателен.
  • Typing: поддержать; события в рамках чата.
  • Presence: online если активность ≤ 60 секунд; Redis; last_seen только контактам.

20. Очереди/события: NATS JetStream

  • Гарантии: at-least-once; повторы возможны; обработчики идемпотентны.
  • Дедуп сообщений: (sender_id, chat_id, client_msg_id) — уникальный индекс/идемпотентная вставка.
Однозначность (namespace в командном dev):
Все subjects имеют namespace: dev.<DEV_NS>.*. Сервисы подписываются/публикуют только в свой namespace.

21. Аудит

  • Аудит: события безопасности/админ-действий/изменений.
  • Хранение: выделенный контур (PostgreSQL с партиционированием) допускается; на 1 этапе — таблицы audit_events.
  • Медиа: модераторские действия (остановить стрим, бан/кик, выдача публичных ссылок) — писать в аудит.

22. Наблюдаемость: Prometheus/OTel + Zabbix

  • Prometheus/Grafana: метрики по каждому компоненту и ноде (NATS lag, DB, proxy).
  • OpenTelemetry: распределённый трейсинг между API/WS/воркерами.
  • Zabbix: infra monitoring хостов/VM/ресурсов и доступности; дополняет Prometheus.
  • Медиа метрики: viewers, bitrate, packet loss, TURN usage, time-to-first-frame, HLS segment errors.

23. Администрирование и организации (multi-tenant)

  • Организации: поддержать (multi-tenant).
  • Роли: системный админ ≠ админ группы.
  • Политики: организации могут владеть политиками (в т.ч. запись стримов, лимиты звонков/качества).

24. Безопасность

  • Секреты: Docker secrets; master key один на окружение.
  • Пароли: Argon2id (или эквивалент); хранить только хэши.
  • Refresh tokens: хранить безопасно (желательно хэш).
  • Base64: не использовать как “экономию”/защиту.
  • Логи: не логировать текст сообщений.
  • E2EE: обязательно для calls и для live ≤200 (WebRTC); без бэкапа ключей, только активные устройства.
  • HLS режим: для live >200 — без E2EE, только TLS.
  • DVR encryption: запись шифруется на клиенте; ключ хранится в защищённом контуре; 1 ключ на запись.
Комментарий для однозначности (ключи и E2EE):
“Ключи хранит сервер” относится к ключам DVR (custody), но не означает бэкап/восстановление E2EE ключей пользователей.

25. Dev-стенды (min/full) + командный dev

Однозначность:
Ресурсы dev относятся к режиму без стресс-тестов. В dev допускается объединение воркеров, но интерфейсы и события должны соответствовать ТЗ.

25.1 Dev-min

  • Состав: API×1, WS×1, worker-all×1, Hot PG×1, Archive PG×1, Redis×1, NATS×1, MinIO×1, ZK×1, Solr×1, media stack (минимум).
  • Ресурсы: 4–6 vCPU, 12–16 GB RAM, 80–200 GB SSD.

25.2 Dev-full

  • Состав: API×1, WS×1, worker-* раздельно, infra single-node, media stack.
  • Ресурсы: 6–8 vCPU, 16–24 GB RAM, 150–400 GB SSD.

25.3 Командный dev (до 10 разработчиков)

  • Shared infra: postgres-hot-dev, postgres-archive-dev, nats-dev, redis-dev, minio-dev, solr-dev+zookeeper-dev.
  • Изоляция БД: avandocmsg_hot_<DEV_NS>, avandocmsg_archive_<DEV_NS>.
  • Изоляция NATS: subjects dev.<DEV_NS>.*
  • Изоляция MinIO: префикс dev/<DEV_NS>/… (или bucket на разработчика).
  • Изоляция Solr: поле namespace=<DEV_NS> + fq=namespace:<DEV_NS>.

25.4 Автоматизация стендов

На чистой машине должны выполняться только: install-environment, create-stand, start, clean. Остальное — автоматические steps по номерам.

26. Production-стенд: стартовый состав и sizing

Однозначность:
Оценки ресурсов — ориентиры под ≥100M сообщений/день. Точные значения требуют нагрузочного тестирования.

26.1 Стартовый набор (production)

Состав совпадает с исходным ТЗ: nginx LBs, messenger-core-api, messenger-ws, workers (message/archiver/deep/indexer/preview/push/bot/export), infra (NATS/Redis/Postgres Hot+Archive/MinIO/Solr+ZK), observability, media stack (signaling/SFU/TURN/ingest/HLS/DVR).

26.2 Sizing (ориентир)

Основные потребители: Hot Postgres (IOPS), Solr (RAM+disk), MinIO (disk+network), WS (connections), Media SFU (CPU+network), TURN (network), HLS (egress).

28. Потоковое видео (Live / Streaming)

28.1 Сценарии и режимы

  • Live и видеозвонки нужны оба: да.
  • Live ведущие: до 5 ведущих одновременно, режим разделения экрана.
  • Модерация показа: админ (создатель стрима) управляет видимостью ведущих; админ может не быть ведущим.
  • Целевая задержка: 2–5 секунд.

28.2 Источники видео

  • Камера клиента: WebRTC.
  • Внешние энкодеры: RTMP и SRT (оба).
  • Stream key: один ключ на стрим, автосоздание при старте; один ключ для RTMP+SRT.

28.3 Масштабирование (порог 200)

  • Прод ориентир: до 10k зрителей на стрим.
  • До 200: WebRTC + E2EE.
  • После 200: HLS без E2EE (TLS).
  • Поведение при росте >200: запрещать рост аудитории и/или создавать “зеркало” стрима (детализация — эксплуатационная спецификация).

28.4 Запись (DVR)

  • Запись: по включению (комбинация политика+роль).
  • Шифрование: client-side encryption; ключ хранится в защищённом контуре; 1 ключ на запись.
  • Доступ: текущие участники группы на момент просмотра; также по публичным ссылкам A/B/C.
  • Публичные ссылки: создавать могут ведущий, админ группы, системный админ.
  • Удаление записи: админ группы, системный админ.

28.5 Модерация live (обязательный набор)

  • остановить стрим админом;
  • запретить стримить участнику;
  • кик/бан зрителей;
  • slow mode/закрыть чат;
  • жалобы/репорты.

28.6 Сеть

  • TCP-only сети: поддержать (TURN/TCP/TLS 443), автодетект.
  • proxy/VPN/tunnel: медиа обязано работать через встроенные режимы клиентов.

29. Аудио/Видео звонки (Calls)

  • 1:1: аудио и видео.
  • Групповые: аудио до 20, видео до 20.
  • Переключение: аудио ↔ видео в рамках одной сессии.
  • Screen sharing: обязателен (720p лимит).
  • Stage mode: обязателен; спикеры до 5; hand raise есть.
  • E2EE: обязательно; только активные устройства, без бэкапа ключей.

30. “Хранилище” (Saved Messages)

  • Модель: особый чат (self-chat), единый на аккаунт.
  • Копия: сохраняем копию; если оригинал удалён/TTL скрыт — копия остаётся.
  • Копируем всё: текст/вложения/метаданные; link preview пересобирается при показе.
  • Дедуп: требуется по всей системе (цель); на 1 этапе допускается полное копирование ради простоты.
  • Редактирование: в “Хранилище” редактирование сохранённых сообщений отсутствует.
  • Поиск: индексируется в Solr; экспорт не нужен.

6.X. Разбиение на контуры (Core + Peripheral services)

Цель:
Гибридная component-based архитектура: минимальное число сервисов на критическом пути сообщений (Core), и вынесенные контуры для тяжёлых задач (Peripheral). Это оптимально для высокой нагрузки.

6.X.1 Core

  • messenger-core-api (Tomcat REST): auth/devices/tokens, users/contacts, chats/membership/roles/invites, messages CRUD + версии, receipts aggregates, blocks/mutes/hidden, file metadata + public links, search endpoints (Solr + ACL post-filter), admin endpoints.
  • messenger-ws-gateway (Tomcat WS): realtime delivery, presence/typing, подписка на NATS, reconnect.

6.X.2 Peripheral (выделенные контуры)

  • Message pipeline: worker-message-pipeline (write/dedup/fanout), archiver, deep-archiver.
  • Search: worker-indexer + SolrCloud; ACL post-filter на сервере.
  • Files: file-proxy (может быть модулем core-api на 1 этапе).
  • Preview: worker-preview.
  • Push: worker-push.
  • Bots: bot-api (опц. модуль core-api), worker-bot-delivery, worker-export-replay.
  • Media stack: signaling/SFU/TURN/ingest/HLS/DVR отдельным пулом.

6.X.3 Владение событиями NATS (пример)

  • msg.send producer: core-api → consumer: worker-message-pipeline
  • msg.event.* producer: worker-message-pipeline → consumers: ws-gateway, indexer, push, bot-delivery
  • media.event.* producer: media-signaling → consumers: ws-gateway, audit-writer (опц.)
Однозначность:
Все события at-least-once; обработчики идемпотентны. Дедуп: сообщения — по (sender_id, chat_id, client_msg_id), боты — по event_id.

27. Вне рамок

  • Подробные спецификации REST/WS/Bot API (эндпоинты, схемы JSON/Protobuf) — отдельные документы.
  • Детальные политики SSRF/allowlist для превью — позже (на 1 этапе allow-all).

Данное ТЗ фиксирует требования из чата и дополняет их разбиением на Core/Peripheral контуры для высокой нагрузки.
